# 工作待办进展与后续计划确认卡

## 适用范围与前置条件

1. 仅用于需要收集进展及后续安排的工作待办通知，或用户明确要求重做该反馈卡。不用于早晚报、资讯推送。历史已触发的通知不自动补卡；用户明确要求重做时可重发。
2. 从任务上下文读取通知渠道要求。需要邮件的场景，必须先取得邮件的真实发送回执再出卡；无邮件发送回执不出卡。聊天和邮件不能互相替代。本技能不授权发送邮件，实际发送仍须遵循既有审批。
3. 卡片发到用户指定的主对话，不发在二级助手聊天。当前助手无法在指定对话发卡时，交由有权限的主责助手发送，不擅自换地方。
4. 当前状态已知则保留并显示，不重复询问；未知时可以先收集状态。不能只有「已完成、部分完成、尚未完成」三个按钮。邮件送达、状态收集和发卡成功都不等于业务完成，不得据此回写记录。

## 生成真正的分步卡

按运行时 `SendToUser` schema 使用 `type: "widget"` 和 `widget.steps`，不以单层选项冒充分步卡，不伪造独立文本框能力。当前每步至少有一个真实选项，实际数量及字段限制以运行时工具为准。若不支持所需结构，如实说明，不声称已经生成同等卡片。

至少包含三步：

1. 具体进展：填写已完成和仍未完成的内容；设置 `allowCustom: true`，可选「暂不补充进展细节」。
2. 后续计划：设置 `allowCustom: true`，可选「暂无后续计划」。需要再次提醒时，收集日期和时间；依据用户时区解释相对日期，并在执行前明确绝对日期、时间和时区。若仍有影响执行的歧义，先澄清，不自行排提醒。跟进时间不是截止时间。
3. 最终确认：明确提供「最终确认，按此执行并更新对应记录」与「尚未最终确认，暂不执行或更新，等最终确认」两个选项。

通用示例；运行时替换为对应事项并保留已知状态，示例中的状态不是默认业务事实：

```json
{
  "type": "widget",
  "widget": {
    "prompt": "工作待办跟进反馈（当前：部分完成）",
    "steps": [
      {
        "prompt": "请填写已完成和仍未完成的具体进展。",
        "options": [
          {
            "label": "暂不补充进展细节",
            "value": "当前状态保持不变，暂不补充进展细节。"
          }
        ],
        "allowCustom": true
      },
      {
        "prompt": "请填写后续计划；如需再次提醒，请写明日期和时间。",
        "options": [
          {
            "label": "暂无后续计划",
            "value": "本次暂无后续计划或再次提醒安排。"
          }
        ],
        "allowCustom": true
      },
      {
        "prompt": "以上进展及后续计划，是否作为最终确认稿？",
        "options": [
          {
            "label": "最终确认，按此执行并更新对应记录",
            "value": "以上是我最终确认的进展及后续计划，请按此执行并更新对应记录。"
          },
          {
            "label": "尚未最终确认，暂不执行或更新，等最终确认",
            "value": "以上反馈尚未最终确认，请暂不执行新增安排，也不要更新对应记录，等我最终确认。"
          }
        ]
      }
    ]
  },
  "end_turn": true
}
```

发送卡片前如需说明，使用单独短文本；卡片是该轮最后一条消息。不要为示范或测试而向用户发送真实卡片。

## 未最终确认：仅暂存在当前对话

选择尚未确认、跳过第三步、仅填前两步、关闭卡片或含糊回复，都不构成最终确认。进展及计划只暂存在当前对话，不建提醒、不执行新增待办、不回写 Notion 或其他对应记录。

普通聊天回复同样按语义识别，不强制复述固定句式；明确确认该稿并授权执行才算终稿。补充、假设、讨论及偏题不当作确认。用户改口或否定时，以最新明确意图为准。仅要求存技能不等于确认实际业务安排。

## 最终确认：只执行授权范围

1. 核对用户最后一次明确确认的终稿，不把此前未确认讨论带入执行。部分完成也可最终确认，确认终稿不等于事项已完成，不擅改为已完成。
2. 已确定的再次提醒，由有权限的父助手或主责助手加载当时提醒规则建立并核验。没有权限则转交，不声称已建立。明确日期、时间、时区和提醒目标，避免重复建立。
3. 回写只关联现有对应事项。无匹配项不擅自新建、不改其他行。只更新终稿授权字段；跟进时间与截止时间严格区分，不覆盖用户手改内容。需要澄清字段冲突时先问清。
4. 新增安排仅按终稿明确授权执行；仍须遵守相应动作审批。用户后续明确单独授权某项时，仅执行该项，不连带执行旧稿其他安排。
5. 不对外联系事项涉及的人，不代为发消息、询问或催办。

## 分项核验与如实反馈

- 邮件前置：核验真实发送回执，不把聊天回执当成邮件回执。
- 卡片发送：核验发到指定主对话的成功回执。接口成功不等于客户端已经显示。用户报告看不到时查实；原因无法确定就说未知，不编造故障原因，不宣称已修复。
- 最终确认：核验用户最后一次明确终稿及授权范围，跳过或未确认不执行。
- 提醒建立：核验实际建立结果、日期时间时区和目标；没有成功结果不说已设置。
- 记录回写：读取核验目标事项及修改字段；发送卡片、邮件送达、收集状态不替代回写验证。

交付时区分已发送、待确认、已设提醒、已回写及受阻事项，只陈述核验过的结果。重发卡片仍遵循同一最终确认边界。
